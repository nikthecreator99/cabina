# Сервер CABINA

Сервер нужен для аккаунтов и (с 2.15) для «Коллег». Без аккаунта CABINA работает как раньше: все записи остаются в телефоне.
Сервер — нужная часть Supabase на облачном сервере Селектела в Москве (152-ФЗ, ст. 18 ч. 5), с 03.11.2026; установка — `server/stack/README.md`. Раздел «Настройка на сервере» ниже описывает прежний сервер Beget (потерян при атаке на провайдера 1–2.11.2026), правила из него действуют и сейчас.

**В этой папке нет и не должно быть секретов.** Репозиторий публичный. Ключи `service_role`, `JWT_SECRET`,
пароль базы и почты создаются на самом сервере и хранятся только там и в менеджере паролей владельца.
Почта администратора тоже не пишется в репозиторий.

## Что хранится на сервере (шаг 1)

| Таблица | Что внутри | Кто видит |
|---|---|---|
| `auth.users` | почта, хеш пароля (встроенный вход Supabase) | сам человек через `export_my_data()` |
| `public.profiles` | роль, дата регистрации, дата последнего захода (без времени), платформа, версия | только сам человек |
| `public.consents` | какой документ и в какой редакции принят, когда | только сам человек |
| `private.invites` | хеш кода-приглашения, срок, кем использован | никто через API |
| `private.stats_daily` | числа за день: регистрации, подтверждения почты, удаления | администратор через `admin_stats()` |

Поездки, заработок, отвлечения и профиль из телефона на сервер не отправляются.

## «Коллеги» (шаг 2, миграция `0002_colleagues.sql`)

Миграция применена на сервере 29.10.2026 (проверено: таблицы под RLS, роль anon получает отказ 401).
Только если человек сам включил. Всё стирается кнопкой «Выйти из „Коллег“» и вместе с аккаунтом.

| Таблица | Что внутри | Кто видит |
|---|---|---|
| `public.cards` | имя, должность; депо и персонаж (набор деталей, не фото) — если разрешено; «меня можно найти» | сам; те, с кем есть предложение или связь; в поиске — все, только при «меня можно найти» |
| `public.links` | предложения и связи «коллеги» (одна запись на пару) | только эти двое; отклонённые — никто (нужны серверу для паузы 30 дней) |
| `public.statuses` | одна строка текущего статуса без истории: вид, часть суток, «до …», что дальше (станции — с 2.16 в `status_places`) | сам и те коллеги, кому он его показывает (`access`), пока не устарел (48 ч без обновления — стирается) |
| `private.limits` | счётчики за день: поиски (100) и предложения (10) | никто через API |
| `public.consents` | + `withdrawn_at` и согласие на распространение `publish-1` (152-ФЗ, ст. 10.1) | только сам человек |

Номер поезда и локомотива, точное время явки, причина и даты отвлечения, телефон сюда не попадают. «Скоро явка» хранит
только начало части суток (без минут). Без согласия текущей редакции (с 2.20 — `privacy-3`) функции «Коллег» отказывают.

## Кому из коллег что видно (шаг 3, миграция `0003_access.sql`, приложение 2.16)

Миграция применена на сервере 30.10.2026, после выпуска 2.16 (перед этим — резервная копия; отпечаток файла сверен; проверено: роль anon получает отказ 401
на `access` и `status_places`). Приложение 2.15 с ней продолжает работать (видит статусы коллег без станций), 2.16 без неё пишет
«на сервере ещё не включён» и статус не отправляет.

| Таблица | Что внутри | Кто видит |
|---|---|---|
| `public.access` | правила «кому видно»: что (`status` — статус, `place` — станции и дом отдыха) и кому (коллега или пусто — все коллеги) | только сам человек; коллега через `private.allowed()` узнаёт лишь «мне можно?» |
| `public.status_places` | станции в пути или дом отдыха из текущего статуса | сам и коллеги, которым он показывает и статус, и «где я»; стирается вместе со статусом |

Нет правила — не видит никто, и сервер такой статус (станции) даже не хранит. Связь «коллеги» пропала — разрешения между
этими двумя стираются (триггер на `links`); снова стали коллегами — разрешают заново. При переносе: кто уже показывал
статус, тому выставлено «все коллеги» и для статуса, и для станций (как было в 2.15).

## Сайт приложения (шаг 4, `server/site/`, миграция `0004_site.sql`, приложение 2.16.1)

Включено 30.10.2026 (проверено: HTTPS, заголовки, `server/` снаружи — 404, `www` → 301 на основной адрес; `0004` применена).

- `cabina-site.sh` → `/usr/local/bin/cabina-site`, расписание `/etc/cron.d/cabina-site` раз в 2 минуты. Всё сетевое (git) делает

  ключей и секретов для выкладки нет. Версия без `index.html`/`sw.js` или со ссылками на другие файлы не выкладывается.
  Версия кладётся в `www/releases/<коммит>`, ссылка `www/current` переключается одним действием, хранятся 3 последние.

- `0004_site.sql`: адрес сайта — обязательная часть согласия на распространение (приказ РКН № 18), поэтому новая редакция
  `publish-2`; кто давал `publish-1`, пропадает из поиска, пока не примет новую.
- Старый адрес на GitHub (Pages) выключен 30.10.2026, после того как Никита перенёс записи копией.

## Приглашения и «Идеи» (шаг 5, миграция `0005_invites_ideas.sql`, приложение 2.20)

Миграция применена 03.11.2026 на новом сервере (Селектел) вместе с 0001–0004. Приложение 2.20 без неё пишет «ещё не включены» и работает как раньше;
приложение 2.19 с ней продолжает работать, но для «Коллег» попросит согласие новой редакции — его даёт только 2.20, поэтому
выпускать 2.20 сразу после применения миграции. Новая редакция основного согласия — `privacy-3`.

| Таблица | Что добавилось | Кто видит |
|---|---|---|
| `private.invites` | кто создал приглашение (`created_by`) и номер для отмены (`id`); сам код — по-прежнему только хеш | никто через API; пригласивший через `my_invites()` — только числа: ждут, пришли, засчитаны (без почты, имён и дат входа приглашённых) |
| `public.profiles` | `active_days` — в сколько разных дней человек заходил (только число, без дат) | только сам человек |
| `public.ideas` | идея по улучшению CABINA: текст 3–500 знаков, дата, ответ (`new` / `accepted` / `declined`) | автор; администратор через `admin_ideas()` — без почты и id автора; другим пользователям не видны (это не переписка) |
| `private.limits` | счётчик идей за день (5) | никто через API |

Приглашённый засчитывается, когда подтвердил почту и заходил в 3 разных дня. Неиспользованное приглашение стирается через
14 дней или по «Отменить»; одновременно — не больше 10. Идея стирается автором в любой момент; с ответом — через год после ответа.

## Функции для приложения

- регистрация — обычный `supabase.auth.signUp` с `options.data = { consent: 'privacy-3', invite, platform, version }` (до 2.20 — `privacy-2`).
  Без согласия текущей редакции (и, пока включён закрытый режим, без живого приглашения) аккаунт не создаётся;
  после регистрации эти данные из аккаунта стираются;
- `touch(platform, version)` — отметка «заходил сегодня»;
- `export_my_data()` — всё, что сервер знает о человеке;
- `delete_my_account()` — удаление аккаунта и всего, что с ним связано (это же отзыв согласия);
- `admin_stats()`, `admin_create_invite()` — только для роли `admin`;
- «Коллеги»: `give_consent(document)` (новая редакция или `publish-1`), `save_card(...)`, `find_colleagues(name, depot, role)`
  (имя от 3 букв, до 20 человек), `offer_colleague(to)`, `answer_colleague(from, accept)`, `drop_colleague(other)`,
  `set_status(...)`, `clear_status()`, `leave_colleagues()`, `set_access(item, all, ids)` (2.16). Читать свои строки `cards`, `links`,
  `statuses`, `status_places`, `access`, `consents` — обычным GET через правила доступа;
- приглашения и «Идеи» (2.20): `create_invite()` (код показывается один раз), `my_invites()` (только числа и свои открытые
  приглашения), `drop_invite(id)`, `send_idea(body)`, `delete_idea(id)`; для `admin` — `admin_ideas()`, `admin_answer_idea(id, accept)`.
  Свои идеи — GET `ideas`.

Писать в таблицы напрямую из приложения нельзя: только эти функции.

## Автотесты («стенд»)

```bash
npm run test:server
```

Тесты поднимают временную базу PostgreSQL (нужны программы PostgreSQL 15+; путь — в `PG_BIN`, если они не в
`/usr/lib/postgresql/*/bin`), ставят упрощённую копию Supabase (`tests/supabase-stub.sql`) и все миграции.
Проверяется: чужой не видит и не меняет мои данные; без входа не видно ничего; у каждой таблицы есть RLS;
удаление аккаунта стирает всё; статистика — только числа и только администратору; IP в журналах — не дольше 30 дней.
Новая таблица без RLS или без `on delete cascade` к `auth.users` роняет тесты.

## Правила изменения базы

- Каждое изменение — новый файл `migrations/NNNN_что.sql`. Старые файлы не правим после выкладки на сервер.
- Новая таблица: RLS, правило «своё», `on delete cascade` к `auth.users`, тест «чужой не видит».
- Новая функция в `public`: `security definer`, `set search_path = ''`, проверка `auth.uid()`, без доступа для `anon`.
- Перед изменением — чек-лист из раздела 1.4 `CLAUDE.md`.

## Настройка на сервере (кратко; пошаговая инструкция — в отдельном документе для владельца)

Состояние на 26.10.2026 (сервер настроен вместе с владельцем, миграция 0001 применена и проверена настоящими запросами):

1. VPS на Beget в России, Supabase из каталога. Вход по SSH только по ключу, пароль для SSH выключен. Подкачка 2 ГБ, автообновления безопасности включены.
2. Наружу открыты только 22 (SSH по ключу), 80 и 443; файрвол ufw включён 30.10.2026 (до этого был выключен, найдено проверкой). Порты базы (5432, 6543) привязаны к `127.0.0.1` в `docker-compose.yml`
   (Docker открывает порты в обход ufw, поэтому смотрим `ss -tlnp` и `docker ps`, а не только файрвол).
3. Caddy (`volumes/proxy/caddy/Caddyfile`) отдаёт наружу только `/auth/v1/*` и `/rest/v1/*`; всё остальное, включая Supabase Studio, — 404.
   Studio открываем только через SSH-тоннель, когда нужна.
4. Настройки входа (`.env`, `docker-compose.yml`): подтверждение почты обязательно, вход по телефону выключен, пароль от 10 символов
   (`GOTRUE_PASSWORD_MIN_LENGTH`), `SITE_URL` — адрес приложения. Вход через Google, Apple, Telegram и т.п. выключен (149-ФЗ, ст. 8 ч. 10).
   Почта: подключить почту Beget на нашем домене (пока заглушка `fake_sender`, письма не уходят).
5. Телеметрия Supabase и любая внешняя аналитика выключены.
6. Миграции применяются по порядку: `docker exec -i supabase-db psql -U postgres -d postgres -v ON_ERROR_STOP=1 --single-transaction < 0001_accounts.sql`
   (файл скачивается из репозитория, отпечаток `sha256sum` сверяется с тем, что назвал Claude).
7. Ежедневная очистка журналов — обычным расписанием на сервере (`/etc/cron.d/cabina-cleanup`, 03:15 по Москве, вызывает `private.cleanup_logs()`),
   `pg_cron` не используем.
8. Первый администратор — после своей регистрации, в консоли сервера:
   `update public.profiles set role = 'admin' where id = (select id from auth.users where email = '…');`
9. Резервные копии (с 29.10.2026): `backup/cabina-backup.sh` → `/usr/local/bin/cabina-backup`, cron `/etc/cron.d/cabina-backup`
   в 00:30 UTC (03:30 МСК), журнал — `journalctl -t cabina-backup`. Схемы `auth`, `public`, `private` (`pg_dump -Fc`), проверка `pg_restore -l`,
   шифрование AES-256 случайным ключом, ключ — открытым RSA-ключом Никиты (`/root/cabina-backup-public.pem`). Закрытый ключ только
   у Никиты (MacBook + флешка), на сервере его нет. Копии в `/root/cabina-backups/`, хранятся 14 дней. Расшифровка на MacBook проверена
   29.10.2026. Пока копии лежат на том же сервере: от «случайно удалили» защищают, от потери сервера — нет; второй слой
   (снимки Beget или копия вне сервера в России) — следующий шаг. Раз в месяц — проверка восстановления во временную базу.
10. Проверка «чужого» на настоящем сервере: регистрация без согласия и без приглашения отклоняется, `anon` не читает `profiles` и не вызывает `admin_stats`.

Менять файлы на сервере: сначала копия `.bak`, потом правка, потом `docker compose up -d` и проверка.

Закрытый режим выключается только перед открытием регистрации для всех:
`update private.config set value = 'false' where key = 'invite_only';`

С шагом 8 (`0008_open_signup.sql`, приложение 2.26) код приглашения погашается и при открытой регистрации — пригласивший
получает засчитанное приглашение; «нужно приглашение» — по-прежнему только в закрытом режиме. Миграцию применить до того,
как выключать закрытый режим. В приложении режим — `SIGNUP_OPEN` в `js/legal.js` (должен совпадать с сервером).

## Группы коллег (шаг 7, миграция `0007_groups.sql`, приложение 2.22)

Применять одновременно с выпуском 2.22: миграция поднимает редакцию согласия до `privacy-4` (регистрация из старого приложения
с `privacy-3` не пройдёт), а 2.22 без миграции пишет «группы ещё не включены» и работает как 2.21.

| Таблица | Что внутри | Кто видит |
|---|---|---|
| `public.groups` | название (до 30 знаков), дата создания | участники; приглашённый — только название |
| `public.group_members` | кто в группе, кто администратор (один), дата вступления, показывает ли он группе статус (`show_status`) и где он (`show_place`) — по умолчанию нет | участники этой группы |
| `public.group_invites` | кого пригласили, кто (администратор), когда; без ответа — 30 дней | приглашённый и администратор группы |
| `private.group_codes` | текущий код группы (10 знаков; хранится как есть, чтобы администратор мог показать его снова; сменить — `group_code(id, true)`) | никто через API; администратор — через `group_code()` |
| `private.group_bans` | кого исключил администратор: 30 дней не вернуться по коду | никто через API |
| `private.limits` | + `groups` (5 групп в день), `group_tries` (20 попыток кода в день), `group_invites` (50 приглашений в день) | никто через API |

Статус человека участники группы видят только если он сам включил «Показывать моей группе» в этой группе (`private.allowed`),
само членство статус не открывает. Если статус никому не показывают (ни коллегам по `access`, ни группам) — сервер его не хранит
(`private.shares`). Карточку участники общей группы видят (`private.group_mate`). Ушёл администратор — права у того, кто дольше
в группе; ушли все — группа удаляется (триггер на `group_members`). «Выйти из „Коллег“» выводит из всех групп.
Неверный код не вызывает ошибку (иначе откатилась бы и сама попытка): `peek_group` и `join_group` отвечают `null`.

## Картинка группы, статус в группе взаимно (шаг 9, миграция `0009_group_pics.sql`, приложение 2.27)

- `public.groups.pic` — описание картинки группы (не картинка): цифра, готовый рисунок или текст до 8 знаков, форма, цвет, шрифт и размер.
  Проверяется `private.clean_pic` (неизвестное — отказ «bad pic»), ставит только администратор: `set_group_pic(group, pic)`, `null` — убрать.
  Видят те же, кто видит группу (участники и приглашённые). Новых персональных данных нет — это свойство группы, как название.
- `private.allowed`: участник группы видит статус другого, только если и сам показывает этой группе свой статус; станции — только если
  и сам показывает «где я». Правила для коллег (шаг 3) не изменились.
- `offer_colleague`: позвать можно и участника общей группы, даже если его нельзя найти поиском (`private.group_mate`).

Применять вместе с выпуском 2.27 (или после): 2.26 с миграцией работает как раньше, 2.27 без неё не сохраняет картинку («ещё не включены»),
а взаимность статуса показывает только сам телефон.

## Уведомления: просьба показать статус, комментарии к идеям (шаг 10, миграция `0010_notices.sql`, приложение 2.28)

- `public.status_asks (asker, target, state, asked_at)` — «коллега просит показать ему мой статус». Строку видит только тот, кого просят (RLS);
  записать можно только через `ask_status(p_to)`: просить можно только коллегу, не чаще раза в 7 дней одного человека и не больше 20 просьб в сутки;
  ответ `sent` / `already` (уже показывает) / `later`. Текста у просьбы нет. Человек отвечает `answer_status_ask(p_asker, p_mute)`:
  «Не сейчас» (`dismissed`) или «Больше не просить» (`muted`: следующие просьбы молча принимаются и никуда не попадают — просящий об этом не узнаёт).
  Просьба стирается сама, когда человек разрешил статус, и при удалении из коллег; `cleanup_logs` стирает старше 30 дней.
- `ideas.admin_note` (до 300 знаков) — комментарий администратора, видит только автор идеи; `ideas.seen_at` — автор открыл ответ.
  `admin_answer_idea(p_id, p_accept, p_note)` (принять / отклонить и/или комментарий), `mark_ideas_seen()` — автор отметил ответы прочитанными.
- `export_my_data` отдаёт просьбы ко мне и комментарии к моим идеям. Новых данных о поездках нет.
- Применять вместе с выпуском 2.28 (или после): 2.28 со старым сервером работает — колокольчик есть, просьбы и комментарии «ещё не включены».

## Часы для коллег (шаг 11, миграция `0011_hours.sql`, приложение 2.31)

- `public.hours (user_id, month, cur_min, prev_min, updated_at, expires_at)` — одна строка на человека, без истории: месяц `'YYYY-MM'`,
  отработано минут в нём и итог прошлого месяца. Нормы, переработки, отвлечений и заработка нет (по «отработано из нормы» видны отвлечения).
- Кому видно — правило `access` с `item = 'hours'` (никому / всем коллегам / выбранным, `set_access`). Видят только коллеги: `private.allowed`
  для `'hours'` группы не учитывает, `private.shares` — тоже. Нет правила — `set_hours` ничего не хранит и стирает старое.
- `set_hours(p_month, p_cur, p_prev)`: месяц — текущий по UTC ± сутки, минуты 0…44 640 (31 сутки). Стирается через 7 дней без обновления
  (`hours_days`, коллеге не видна уже после срока — RLS, сама строка — в `cleanup_logs`), при «Никто», удалении из коллег (`tidy`),
  «Выйти из „Коллег“» и удалении аккаунта. `export_my_data` отдаёт `colleagues_hours`.
- Новая редакция согласия `privacy-5`. Применять одновременно с выпуском 2.31: 2.30 после миграции не сможет зарегистрировать новых людей
  (редакция privacy-4), а 2.31 без миграции пишет «часы на сервере ещё не включены» и работает как 2.30 — только для «Коллег» попросит
  согласие privacy-5, которое старый сервер не примет. Поэтому: сначала резервная копия, потом миграция, сразу за ней — выпуск приложения.
